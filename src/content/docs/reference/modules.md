## モジュール名

1つのファイルが1つのモジュールです。ソースのルートからのパスを、区切りごとに snake_case から PascalCase へ変えて `.` でつないだものがモジュール名になります。`src/http/client.emel` は `Http.Client` です。ファイルの中でモジュールを宣言する構文はありません。

- ファイル名とディレクトリ名は小文字の snake_case でなければなりません。`Foo.emel` は E2001、`My-Dir/` は E2001 です。名前の正しくないディレクトリの中のファイルはモジュールになりません。診断はそのディレクトリに1つだけ出します。
- 変換後の名前は型名（大文字で始まり、小文字を1つ以上含む）でなければなりません。`a.emel`（`A`）や `x_y.emel`（`XY`）、ASCII 以外の文字を含む名前は E2001 です。
- `_` の直後の数字はそのまま残ります。`http_2.emel` は `Http2` になり、`http2.emel` と重複します。
- 同じモジュール名になるファイルが2つあれば E2003 です。パスの順で先のファイルを残し、後のファイルに診断を出します。大文字小文字だけが違うファイルも重複として扱います。
- `.` で始まるファイルとディレクトリ、`.emel` 以外のファイルは無視します。
- ソースのルート直下の `prelude.emel`、core のモジュールと同じ名前のファイル（`list.emel`、`string.emel` など）、`std.emel` と `std/` は予約されていて置けません（E2002）。std のモジュールは `Std` の下に置くので、std にモジュールが増えても予約された名前は増えません。
- ディレクトリは名前の順にたどるので、診断の順序は毎回同じです。
- モジュールどうしの import の循環は E2005 です。互いに import しあうモジュールの組ごとに、診断を1つ出します。自分自身の import も長さ1の循環として扱います。存在しないモジュールの import（E2004）は循環の検出に数えません。

## プロジェクトと単独ファイル

`Pome.toml` を置いたディレクトリがプロジェクトで、`src/` がソースのルートです。

- `emela` のコマンドに渡したパスは、シンボリックリンクを解決した絶対パスにしてから、祖先をたどって `Pome.toml` を探します。最初に見つかった `Pome.toml` のディレクトリがプロジェクトです。
- ディレクトリを渡して `Pome.toml` が見つからなければ E2301 です。
- プロジェクトのエントリは `src/main.emel`、ライブラリのルートは `src/lib.emel` です。両方を置いてもかまいません。`lib.emel` は、プロジェクトが依存されたときのルートのモジュールになります。
- `main.emel` がなければ `emela run` はできません（E2009）。`lib.emel` だけのプロジェクトでは、`check` と `test` のエントリは `lib.emel` で、`build` は検査だけをします。どちらもなければ、`check` は通り、`build` と `run` は E2007 です。
- ファイルを渡して `Pome.toml` が見つからなければ、単独ファイルとして扱います。そのファイルがエントリで、モジュールは同じディレクトリの直下の `.emel` だけです。サブディレクトリと祖先は見ません。
- 単独ファイルでは、エントリから import でたどれるファイルだけを読んで検査します。たどれない隣のファイルの誤りは診断に出ません。名前の誤りと予約された名前の診断はエントリのファイルにだけ出し、重複の診断は import でそのモジュール名に達したときだけ出します。
- エントリのファイルが名前の誤りでモジュールにならないときは、名前の診断に加えて E2008 を出し、ほかのファイルは読みません。
- ファイルを渡して `Pome.toml` が見つかったのに、そのファイルがソースのルートにもテストのルートにもないときは E2006 です。
- 出力先は、プロジェクトなら `<プロジェクト>/target/emela/<ターゲット>`（`js`、`native`、`wasm`）、単独ファイルならそのファイルのディレクトリの `target/emela/<ターゲット>` です。
- 診断のパスはプロジェクトからの相対パスです（単独ファイルではファイルのディレクトリから）。

### テストのルート

`<プロジェクト>/test` はテストのルートで、テストでだけ使うモジュールを置きます。

- モジュール名はテストのルートからのパスで、ソースのルートと同じ規則で決めます。ソースのルートのモジュールと同じ表に入るので、両方に同じ名前があれば重複（E2003）です。
- 予約された名前はソースのルートと同じで、加えて `main.emel` と `lib.emel` も置けません（E2002）。
- テストのルートを読むのは `check`、`test`、言語サーバーで、`build`、`run`、`doc` は読みません。`build` や `run` にテストのルートのファイルを渡すと E2006 です。
- テストのルートのモジュールは、ソースのルートのモジュール（非公開の定義は見えません）、テストのルートのほかのモジュール、`[dependencies]` と `[dev-dependencies]` の Pome を import できます。
- ソースのルートのモジュールからテストのルートのモジュールや `[dev-dependencies]` の Pome を import すると E2010 です。
- 単独ファイルにはテストのルートがありません。

テストの書き方は [テスト](/guide/testing/) にあります。

### 依存する Pome のモジュール

依存する Pome のモジュールは、その Pome のルートの名前の下に見えます。`src/lib.emel` がルートのモジュール（`Quince`）で、`src/router.emel` は `Quince.Router` です。

- import の名前は、import を書いたモジュールが属す Pome から引きます。先にその Pome 自身のモジュール、次に自分の `[dependencies]` のルートの名前、最後に core のモジュールの順です。
- 依存の依存は見えません。import できるのは自分の `[dependencies]` に書いた Pome と、テストからは `[dev-dependencies]` の Pome だけです。
- 依存する Pome のテストのルートは見えません。

ルートの名前の決め方と変え方は [Pome](/tools/pome/) にあります。

## import

```emela check
import Std.Console.{Console, SystemConsole}

fn main() {
  with SystemConsole {
    (use Console).print_line("hello")
  }
}
```

- `import A.B` は最後の名前 `B` をモジュールとしてスコープに入れます。波括弧の形（`import A.B.{x}`）でも `B` はスコープに入ります。
- 修飾なしで書けるのは、波括弧で列挙した名前だけです。全部を取り込む書き方はありません。別名（`as`）もまだありません。
- 波括弧で列挙した名前は、その名前を持つすべての名前空間から公開された定義を取り込みます。type なら型と構成子の両方です。enum のバリアントも名前で個別に取り込めます。
- import はファイルの先頭に置きます。宣言より後ろの import は E1201 です（コメントは宣言として数えません）。
- import した名前は再公開しません。ほかのモジュールから引けるのは、そのモジュールが定義した名前だけです。
- 同じ定義を2回 import しても重複になりません。名前が同じ別の定義を2つ import すると E2103 です。
- 列挙した名前が見つからなければ E2102、見つかってもどれも `pub` でなければ E2104 です。
- 存在しないモジュール（E2004）と循環（E2005）の診断は、import 文全体でなくパスの部分（`import A.B.{x}` の `A.B`）を指します。

```emela check=error
fn main() {}

import Std.Console    # error[E1201]: imports must come before declarations
```

### core と Std

- 同梱の core のモジュール（`List`、`String`、`Int`、`Int64`、`Float`、`Bool`、`Option`）は、import なしで `.` の左に書けます。
- 型の位置で名前 X がどこにも見つからず、同じ名前の core のモジュール X に型 X があれば、その型になります。`Option[List[User]]` は import なしで書けます。この規則は自分で書いたモジュールには当てはまりません。
- core のモジュールはソースのモジュールと同じ表に入り、単独ファイルでも常に読みます。import なしで書けるのは、名前が1つの区切りだけの core のモジュールです。
- Immediate と Async は import なしで見えます。
- 同梱の std のモジュールは `Std` の下にあり、import が要ります。import せずに `Std` を書くと E2101 です。

```emela check=error
fn main() {
  out = use Std.Console.Console   # error[E2101]: cannot find module or trait `Std` in this scope
}
```

## pub

- 宣言は既定で非公開です。`pub` を付けられるのはトップレベルの宣言（`fn` `type` `enum` `error` `effect` `handler` `layer` `const` `trait`）だけです。
- 非公開の定義をほかのモジュールから参照すると E2104 です。`M.x` で非公開の定義を引いたときは、E2104 を出したうえで、その定義に解決したものとして検査を続けます。
- フィールドやバリアントを個別に公開・非公開にする指定はありません。type の構成子と enum のバリアントは、親の型の `pub` と `opaque` に従います。
- trait の関数も trait の公開範囲に従います。`pub` の trait の関数はほかのモジュールから呼べ、`pub` でない trait の関数は呼べません（E2104）。
- 公開する関数の戻り値の型、`fails` 節、`uses` 節は省けますが、省くと linter が警告します。LSP は推論した型を挿入できます。引数の型は省けません。

## opaque

`opaque` は型の名前だけを公開して、中身を隠します。type と enum にだけ、`pub` と一緒に付けます。それ以外に付けると E1205 です。

| 宣言 | 型名 | 構築 | パターンマッチ | フィールドの参照 |
|---|---|---|---|---|
| `pub type` / `pub enum` | 公開 | 公開 | 公開 | 公開 |
| `pub opaque type` / `pub opaque enum` | 公開 | 定義モジュールの中だけ | 定義モジュールの中だけ | 定義モジュールの中だけ |

- 定義モジュールの外での構築は E2105 です。部分更新（`..式`）も構築として扱うので、外では E2105 になります。
- 外でのフィールドの参照は E2105、パターンでの分解は E2105 です。
- 定義したモジュールの中では、ふつうの type と enum と同じに扱います。

## 名前空間

名前は型・構成子・値の3つの名前空間と、モジュール名に分かれます。

| 名前空間 | 含まれるもの |
|---|---|
| 型 | type、enum、error、effect、handler、layer、trait |
| 構成子 | type の構成子、enum のバリアント、error、フィールドのある handler |
| 値 | fn、const |

どの名前空間を引くかは名前を書いた位置で決まります。

- `.` の左では、モジュールと Trait を引きます。エフェクトも引きますが、それはハンドラメンバーを名指すとき（`Files.Open`）だけです。
- 型の位置では、型だけを引きます。
- 式とパターンの型名では、構成子だけを引きます。

そのため、モジュール `Email` とその中の型 `Email` は衝突しません。`import Email` だけで型 `Email` を修飾なしで書くと E2106（モジュールで、型ではない）です。`Email.Email` と書くか、`import Email.{Email}` で型を取り込みます。

- `.` の左の名前は、モジュールの定義と import から引き、見つからなければ組み込みのモジュールと Prelude の Trait から引きます。同じ段階でモジュールと Trait の両方が見つかれば E2107 です。モジュールとエフェクトの両方が見つかったときは、エフェクトにハンドラメンバー M があれば `X.M` はそれを指し、なければモジュールの定義 M を指します。
- `A.B.f` の B は、モジュール A の `pub` な Trait に限ります。入れ子のモジュールはありません。エフェクトの操作を名指しすることはできません（`Logger.info` はコンパイルエラー）。名指せるのはハンドラメンバーだけです。
- メソッド呼び出し（`x.f(...)`）は、スコープを見ずに x の型を定義したモジュールの関数を引きます。そのモジュールを import する必要はありません。Trait の関数は、呼ぶモジュールで修飾なしに書ける Trait からだけ引きます。
- handler、layer、trait を型の位置に書くと E2106、エフェクトを書くと E2110 です。`fails` 節にはエラーと型引数だけ、`uses` 節にはエフェクトと型引数だけ、`use X` にはエフェクトだけ、`with` と layer の中にはハンドラか layer（とラベルの項目）だけ、制約、derive、impl、上位の Trait には Trait だけを書けます。ほかは E2106 です。
- escape の腕の一番外の構成子パターンはエラーに限ります（E2106）。`_` は書けます。変数は名前の解決を通りますが、型検査で E3203 になります。
- `self` はハンドラの操作と release の中で見えます。init の中では見えません（init はハンドラの値を作る側のため）。フィールドのあるハンドラには同じ名前の構成子があり、init の中で `PostgresUsers(conn: ...)` と書けます。

### 重複と隠すこと

- 同じ名前空間での定義の重複は E2103 です。エフェクトの操作、Trait の関数、フィールド、型引数の並びで同じ名前を2回宣言するのも同じです。同じモジュールの2つの enum が同じ名前のバリアントを持つ場合や、`type Green` とバリアント `Green` も重複です。
- 1つのパターンか引数の並びで同じ名前を2回束縛すると E2109 です。束縛では右辺を先に解決し、その後でパターンの名前を足します。
- モジュールの定義と import は Prelude の同じ名前を隠せます。隠したときは警告します（W2102）。Prelude に名前が足されても、既存のコードが壊れないようにするためです。同梱の core のモジュールの中では W2102 を出しません。

```emela check
enum Maybe {
  Some(Int) # warning[W2102]: `Some` shadows the prelude's `Some`
  Nothing
}

fn main() {
  dbg(Some(1)) # このモジュールの Some
  ()
}
```

### ローカルの fn

- ブロックの中の fn は、宣言からブロックの終わりまでと、自分の本体の中で、値の名前空間に名前を束縛します。宣言より前からは見えないので、ローカルの fn どうしで相互に再帰はできません。
- ブロックの中では、同じ名前のトップレベルの fn、const、import を隠します。後の束縛や同じ名前のローカルの fn に隠されます。どれも警告しません。
- 本体の中では、同じ名前の引数がなければ、自分の名前は自分自身を指します。
- ローカルの fn の中の型名は、囲む宣言のスコープ（その型引数を含む）で解決します。
- 名前はブロックの中でしか見えないので、メソッド呼び出しでは見つからず、テストからも呼べません。

```emela check
fn label(n: Int) -> String { "top #{n}" }

fn main() {
  dbg(label(1))
  fn label(n: Int) -> String {
    if n <= 0 { "local" } else { label(n - 1) }
  }
  dbg(label(2))
  ()
}
```

```console
$ emela run main.emel
"top 1"
"local"
```

最初の `label(1)` はまだローカルの fn の宣言より前なので、トップレベルの `label` を呼びます。ローカルの `label` の本体の中の `label` は自分自身です。
